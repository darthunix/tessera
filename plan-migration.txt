  # Создание Tessera и поэтапный перенос из pg_batch

  ## Кратко

  Создать новый репозиторий /Users/darthunix/git/tessera с чистой историей и лицензией PostgreSQL. pg_batch остаётся неизменяемым образцом поведения и
  производительности.

  Главный внешний контракт Tessera — C API:

  - типы Tess*;
  - функции tess_*;
  - константы TESS_*;
  - заголовки <tessera/...>.

  Расширение tessera предоставляет общий мост. Внутренние вычислительные части постепенно переносятся в Rust, но подключаются к PostgreSQL только через C API.

  Каждый пункт ниже выполняется отдельным небольшим коммитом. Целевой предел — до 300 строк производственного кода, без учёта тестов и документации. При превышении
  500 строк работа автоматически делится на несколько самостоятельно собирающихся коммитов. Тулинг вне библиотеки (tools/) лимитом не ограничен,
  но проходит те же проверки.

  Работа идёт сериями: план серии согласуется до начала, каждый коммит серии собирается и проходит проверки самостоятельно, ревью проводится
  по серии. После серии:

  1. выполнить проверки;
  2. показать краткое описание API, diff и результаты;
  3. остановиться для ревью;
  4. внести замечания в те же коммиты;
  5. только после подтверждения начинать следующую серию.

  ## Начальная структура

  tessera/
  ├── include/tessera/       публичный C API
  ├── bridge/                расширение PostgreSQL `tessera`
  ├── runtime/               C-обвязка PostgreSQL
  ├── crates/
  │   ├── tessera-core/      безопасные структуры и алгоритмы
  │   ├── tessera-kernels/   вычислительные ядра
  │   ├── tessera-spill/     блоки временного хранения
  │   └── tessera-capi/      единая граница Rust → C
  ├── nodes/                 типовые пакетные узлы
  ├── examples/              независимые источники и узлы
  ├── tools/
  │   ├── tessera-bench/     сравнение ревизий по счётчикам
  │   └── tessera-pmu/       PMU-счётчики для произвольного кода
  ├── tests/                 C, Rust и SQL-проверки
  ├── docs/                  устройство и руководства
  └── patches/postgres/      минимальные необходимые патчи ядра

  Бенчмарки библиотеки лежат рядом с крейтами (crates/tessera-capi/benches); отдельного каталога benchmarks/ нет.

  Сборка остаётся смешанной:

  - Cargo собирает Rust-крейты и одну статическую библиотеку C ABI;
  - Meson собирает переиспользуемые C-библиотеки;
  - PGXS собирает расширения PostgreSQL;
  - корневой Makefile запускает эти части в правильном порядке.

  Публичные C-заголовки пишутся вручную. Rust-представления проверяются на совпадение размеров и выравнивания отдельными межъязыковыми тестами.

  ## Логические типы и физические представления

  Логический тип колонки и её физическое представление независимы:

  - тип PostgreSQL, typmod, collation и семантика операции берутся из Var, выражения и TupleDesc;
  - TessLayout только связывает позиции целей плана с колонками пачки и не дублирует сведения о типах;
  - физическое представление принадлежит TessBatch и открывается источником через необязательный именованный и версионируемый интерфейс;
  - физическое представление нельзя определять только по OID типа PostgreSQL.

  Runtime выбирает нативное ядро только при совпадении типа PostgreSQL, операции, collation и физического представления. Скалярный аргумент можно один раз
  преобразовать в формат источника вместо преобразования всей колонки. Если точное совпадение семантики доказать нельзя, используется обязательный запасной путь
  через Datum.

  OID пользовательских типов определяется через системный каталог во время выполнения и не входит в постоянный ABI. Расширения могут использовать частные
  нативные интерфейсы между своими компонентами, но общий путь через Datum должен работать между незнакомыми расширениями.

  ## Последовательность коммитов

  ### 1. Основа репозитория

  1. Создать Git-репозиторий с веткой main, лицензией PostgreSQL, README.md и правилами разработки.
  2. Зафиксировать архитектурные правила: граница C/Rust, владение памятью, отсутствие PostgreSQL-вызовов из Rust и порядок ревью.
  3. Не добавлять remote и не копировать историю pg_batch.

  ### 2. Мост Tessera

  2. Добавить TessRowMask и операции над битовой маской строк.
  3. Добавить форматно-независимый TessBatch, обязательную ленивую выдачу колонок как Datum в качестве общего запасного пути, таблицу операций и правила владения
  пачкой.
  4. Добавить TessLayout и TessRequest с раздельными масками колонок фильтра и ленивой проекции.
  5. Реализовать привязку запроса к TupleTableSlot: attach, find, seal и detach.
  6. Реализовать жизненный цикл пачки: publish_batch, get_batch, mark_consumed, is_consumed и release_batch. Выбор текущей строки остаётся частью будущих входных и
  выходных адаптеров runtime.
  7. Добавить реестр источников с устойчивыми именами, не закрепляя интерфейс планирования до появления первого потребителя.
  8. Выполнить позже, вместе с пунктом 6.5: добавить контракт планирования источника и классификацию условий UNSUPPORTED, PRUNE_ONLY, EXACT при подключении
  источника сжатых таблиц к узлу чтения.
  9. Добавить реестр пакетных узлов.
  10. Добавить два независимо собираемых тестовых модуля: поставщик пачки и потребитель. Они не должны использовать закрытые структуры моста.
  11. Написать docs/bridge.md с полным примером, временем жизни указателей, правилами ошибок и схемой передачи пачки.

  До первого публичного выпуска rendezvous называется tessera.api.v0. Версия ABI 0 означает, что интерфейс ещё может меняться после ревью.

  ### 3. Базовые части на Rust

  1. Добавить Cargo workspace, tessera-core и tessera-capi.
  2. Реализовать безопасные Rust-представления TessRowMask, validity bitmap и заимствованных колонок.
  3. Добавить физические представления для плотных int32 и PostgreSQL Datum без промежуточного копирования. Первые C-потребители плотного int32 работают только с
  INT4OID; само Rust-представление не зависит от типов PostgreSQL.
  Обобщённый интерфейс чтения — трейт ColumnReader: get для одиночных строк, word_values по словам выборки и try_fold_selected
  (реализация по умолчанию через word_values, любой тип значения) для сокращений по одной колонке. Построчного итератора нет:
  несколько колонок обходятся в lockstep через zip их word_values по одному слову. NULL в плотном представлении читается без
  зависимой от данных ветви (копия ячейки как MaybeUninit и выбор нуля); потребители складывают через map_or, а не if let,
  чтобы не удлинять цепочку зависимостей аккумулятора.
  4. Перенести обычный фильтр сравнений int32.
  5. Постоянные бенчи чтения и обычного фильтра int32 измеряют PMU-счётчики, а не время: инструкции, такты и промахи ветвлений на вызов
  через тулинговый крейт tools/tessera-pmu (kperf, macOS, root). Инструкции детерминированы и не зависят от ядра, частоты и состояния
  предсказателя; у наносекундных операций нет разрешения по времени. Общие входные данные и независимые Rust-эталоны сохраняются.
  Утилита tessera-bench сравнивает совместимые ревизии одной командой, собирая изолированные снимки: на каждый случай три пары
  процессов до/после, чередуясь (инструкциям хватает одного процесса, тактам нужны несколько состояний ядра). Пороги: FAIL при росте
  инструкций на вызов более чем на 1%; FAIL при росте минимума тактов более чем на 10% на операциях от 500 тактов; предупреждение
  при росте минимума тактов более чем на 3% (или на 4 такта у операций короче 200 тактов); любой вердикт по тактам требует, чтобы и
  медиана выросла за порог предупреждения — настоящее замедление сдвигает всё распределение, а один удачный блок только минимум;
  пометка MODES при расхождении процессов или блоков более чем в 1,10 раза и более чем на 10 тактов — код с несколькими режимами
  стоимости, минимум сравнивает его лучший режим; блоки и процессы одной стороны должны совпадать по инструкциям в пределах 0,1% и
  не содержать нулевых показаний, иначе UNSTABLE. Эталон показывается как отношение инструкций и тактов и не влияет на статус;
  отчёт печатает инструкции и такты на строку и IPC. Повторов до PASS нет; исходные показания сохраняются.
  Подробности запуска и проверки — в руководстве бенчмарков.
  Такты нестабильны там, где код имеет несколько режимов: на коротких операциях они зависят от состояния ядра и раскладки кода;
  при разборе предупреждения смотреть минимум и медиану по блокам и промахи ветвлений. Замедление без роста инструкций (например,
  удлинение цепочки зависимостей) ловится только тактами и ручным разбором.
  Входные данные бенчей включают и регулярные паттерны (предсказатель их выучивает, ветви по данным стоят ноль), и случайные с
  фиксированным зерном (`random`, `nulls-random`), на которых ветвь по данным видна; оценивать код по обоим.
  Отдельно проверить исходный C-фильтр pg_batch без SIMD тем же прибором: tessera-pmu считает любой код на потоке, C-фильтр вызывается
  через FFI из Rust-бенча. Затем отдельным коммитом проверить SIMD только для AArch64 с обычным запасным путём; оставить его лишь при
  воспроизводимом выигрыше по тактам (минимум по блокам; инструкции SIMD уменьшает всегда, поэтому критерием быть не могут) на целевых
  случаях без значимых потерь в остальных. SIMD для x86 не добавлять без возможности проверить его скорость; возможность и план — п. 3.9.
  Если SIMD не даёт выигрыша, обычный фильтр остаётся основной реализацией; сам по себе SIMD не является обязательным результатом пункта.

  битами non-NULL или Datum-значения с флагами), только для полных слов. NEON-фильтр в tessera-kernels (изолированный модуль simd.rs,
  unsafe только для векторных загрузок) сравнивает слово целиком: веса полос + addv, для Datum uzp1 и отдельная упаковка флагов.

  и на 0–1 строке (+2…4). Уроки: цикл по строкам держать в функции с проверкой длины буфера (иначе проверка границ на строку);
  источник выборки — типом, не Option в цикле; бенч hash_int32 (hash, hash_group, two_keys, reference).
  9. SIMD для x86-64: AVX2. Решение (2026-09-20); выполняется после 6.3, до 4.15 и раздела 5 (см. порядок перед разделом 5).
  Группа: AVX2 (уровень x86-64-v3: AVX2, BMI1/2, FMA — нужны только целочисленные AVX2). Причины: есть на всех Intel Mac с 2013 г.
  и на всех серверных x86 последних десяти лет, включая AMD Zen; AVX-512 есть лишь на части Xeon и на Zen 4+, среди Mac — только
  13" 2020 (Ice Lake), и на старых Xeon он снижает частоту; 256 бит = 8 полос int32, слово из 64 строк — 8 групп вместо 16 у NEON.
  AVX-512 (VL/BW, маски в регистрах) — отдельной третьей группой позже и только под конкретную машину, где её можно измерить.
  Диспетчеризация: без флагов -C target-cpu (расширение должно работать на любом x86-64); на x86_64 блочный путь включается
  только при is_x86_feature_detected!("avx2") (std кеширует ответ), проверка входит в решение по первому слову вместе с
  остальными условиями; без AVX2 — построчный путь, как на прочих целях. На AArch64 NEON остаётся базовым, статически.
  Устройство кода: simd/ делится на simd/neon/{mod,filter,arith,aggregate,hash}.rs (текущий код без изменений — его форма
  выверена дизассемблером, п. 3.6–3.8) и simd/avx2/{…}.rs с теми же именами точек входа; simd/mod.rs реэкспортирует модуль
  своей архитектуры и даёт simd::available(). Общего trait над полосами не вводить: две параллельные реализации под одним
  контрактом дешевле, чем обобщение, которое перестраивает кодогенерацию NEON (уроки 3.6: замыкания по значению, состояние в
  цикле). Гейты в int32/* — cfg(any(target_arch = "aarch64", target_arch = "x86_64")) плюс simd::available(); стабы для прочих
  целей и Miri остаются. Точки входа AVX2 — безопасные обёртки с одним unsafe-вызовом функции с #[target_feature(enable =
  "avx2")] после проверки признака (у NEON проверка const, у AVX2 — времени выполнения).
  Соответствия NEON → AVX2: сравнение → _mm256_cmpeq/cmpgt_epi32 (lt/le/ge через перестановку операндов и инверсию), биты
  слова — _mm256_movemask_ps на результате сравнения, 8 бит на группу, вместо весов и горизонтального сложения; флаги NULL —
  _mm256_cmpeq_epi8 с нулём и _mm256_movemask_epi8, два раза по 32 байта; маски полос из битов — broadcast байта, and с весами
  1<<lane, cmpeq; Datum → int32 — две загрузки по 4 Datum и выбор младших двойных слов (_mm256_shuffle_ps/permute4x64 или
  permutevar8x32); арифметика — _mm256_add/sub_epi32 с проверкой переполнения через расширенное сложение (cvtepi32_epi64) или
  знаковые трюки, умножение — _mm256_mullo_epi32 с проверкой через _mm256_mul_epi32 по чётным и нечётным полосам; волшебное
  деление — _mm256_mul_epi32 по чётным и сдвинутым нечётным полосам и сборка старших половин, сдвиги _mm256_srav_epi32;
  murmur32 — _mm256_mullo_epi32, сдвиги, xor; суммы/min/max — _mm256_add_epi64 после cvtepi32_epi64, _mm256_min/max_epi32.
  Тесты: существующие сравнения вектор против построчного пути и против скалярной формулы (filter, arith, divisor, hash,
  aggregate) выполняются и на x86_64; тест AVX2 не имеет права тихо пропускаться — при TESSERA_REQUIRE_SIMD=1 отсутствие
  признака есть ошибка. Прогон до Intel-ноутбука — на M5 под Rosetta 2 (macOS ≥ 15 транслирует AVX2; кросс-компиляция в
  x86_64-apple-darwin Rosetta не требует, нужна только для запуска): rustup target add x86_64-apple-darwin; cargo test --target
  x86_64-apple-darwin -p tessera-kernels; первой командой проверить, что is_x86_feature_detected!("avx2") под Rosetta истинен на
  этой машине (sysctl под arch -x86_64 показывает 0 ARM-хоста и ничего не доказывает), иначе корректность только на Intel.
  Измерения: PMU через Rosetta непригодны — kperf считает ARM-инструкции и такты Apple-ядра на транслированном коде (256-битная
  операция AVX2 становится двумя NEON или длинной последовательностью), отношение тактов вектор/построчный путь может даже
  перевернуться; других способов измерить x86 на M5 нет (QEMU без PMU, Linux по решению не используется). Только на Intel Mac
  (kperf/kpc работают и там; в kpep-базе имена событий Intel — INST_RETIRED.ANY, CPU_CLK_UNHALTED.THREAD,
  BR_MISP_RETIRED.ALL_BRANCHES, BR_INST_RETIRED.ALL_BRANCHES). tools/tessera-pmu получает таблицу событий по семейству
  процессора; флаг «только пользовательский уровень» проверяется заново; перед любой приёмкой — та же калибровка, что на M5
  (одинаковые бинарники → 0 FAIL; синтетика; минимумы ≥ 500 тактов), пороги пересматриваются по сырым данным Intel (турбо и
  гипертрединг вместо мод M5). Правило приёмки 3.5 без изменений: вектор остаётся при воспроизводимом выигрыше по тактам,
  инструкции критерием не служат; перед прогоном — diff дизассемблера экземпляров bulk с базой (objdump x86_64-сборки — это
  делается на M5 без Rosetta).
  Когда: после 6.3 и до 4.15 и раздела 5 — к этому моменту набор ядер первой цепочки (фильтр, арифметика, агрегаты, хэши)
  зафиксирован, а ядра раздела 5 (групповой агрегат, hash join) уже пишутся сразу для обеих архитектур на готовой
  инфраструктуре (раскладка модулей, диспетчеризация, тестовая цель, PMU на Intel, калибровка). Подготовка не ждёт очереди:
  правки только в tessera-kernels и tools/tessera-pmu, поэтому тесты под Rosetta и порт simd/avx2 можно вести параллельно с
  4.10–4.14, а приёмку по счётчикам делать, когда доступен Intel-ноутбук. Коммиты по ядрам: filter → arith (с делителем) →
  aggregate → hash, каждый со своей приёмкой, как в 3.4–3.8. Документация: docs/kernels.md (две архитектуры, диспетчеризация),
  crates/tessera-capi/benches/README.md (платформы: macOS на Apple silicon и Intel), «Принятые ограничения» — про счётчики
  без изменений (macOS, kperf).

  Чистые крейты запрещают unsafe. Небезопасный код допускается только в tessera-capi, изолированных SIMD-модулях и тулинговом крейте
  tools/tessera-pmu (FFI kperf), который не линкуется в библиотеку. Каждый блок unsafe получает комментарий SAFETY.

  Rust не вызывает PostgreSQL, в том числе косвенно через указатели на функции, и не хранит TupleTableSlot, MemoryContext или Datum-указатели после возврата.

  Правила паник и ошибок:

  - Раскрутка стека разрешена только внутри Rust. В корневом Cargo.toml для dev и release явно задаётся panic = "unwind"; panic = "abort" не поддерживается.
  - Rust-функции, вызываемые из C, используют extern "C", не extern "C-unwind". Весь потенциально паникующий код выполняется под catch_unwind внутри
  Rust-функции до возврата в C. Пойманная паника превращается в ошибку TessStatus. Сам по себе extern "C" не заменяет перехват: выход паники к этой границе
  аварийно завершает процесс.
  - Обычные ошибки возвращаются через Result и TessStatus, а не panic. Перехват паники не откатывает изменения: частичный результат не выдаётся, а затронутое
  состояние должно быть восстановлено или исключено из дальнейшего использования. AssertUnwindSafe допустим только с объяснением сохранности состояния.
  - Освобождение ресурсов, обработка ошибки и уничтожение объекта пойманной паники не должны вызывать новую панику. Перехват не защищает от abort,
  повреждения памяти или повторной паники при раскрутке стека.
  - ERROR PostgreSQL использует siglongjmp и не перехватывается catch_unwind. Rust сначала возвращает статус в C; только после этого C может вызвать
  ereport(ERROR). Переход через активные Rust-вызовы запрещён, поскольку он обходит освобождение Rust-ресурсов.
  - Глобальный обработчик паник не заменяется библиотекой и не вызывает PostgreSQL: он выполняется до перехвата паники.

  В пункте 3.1 добавляются настройки сборки и описание этих правил, без искусственных C-функций и TessStatus. Перехват и статус добавляются вместе с первой
  настоящей C-функцией. Одновременно проверяется вызов из C с искусственной паникой: возврат ошибки, освобождение ресурсов, отсутствие частичного результата
  и безопасное состояние после ошибки. Проверка выполняется с обычной и release-библиотекой; одного cargo test недостаточно, поскольку тестовая сборка
  отдельно обрабатывает настройку panic.

  9. Раскладка структур Rust в общей памяти и проверка параллельных протоколов — выполняется до 5.4, чтобы серийный hash join сразу
  строился в этой раскладке, а 5.7–5.8 на неё опирались. Раскладка: таблицы соединения и группировки, чанки build-стороны, каталоги
  разделов spill живут в памяти, выделенной C (DSA, dsa_allocate), с заголовком фиксированного формата; Rust получает их как
  заимствованные байтовые буферы; все внутренние ссылки — смещения (u32/u64 от начала региона или dsa_pointer), никогда локальные
  адреса процесса; ёмкость задаётся при создании, рост — через C; аллокаций в Rust нет; атомарные операции — AtomicU32/AtomicU64 поверх
  сырых указателей на выровненную память (вставка в корзину через CAS, публикация чанка через release/acquire), никакого неатомарного
  доступа к разделяемым словам; код — в одном изолированном модуле с unsafe и комментариями SAFETY, как simd; C владеет временем жизни
  (ShutdownCustomScan), Rust не хранит указатели после возврата. Проверка loom (обязательно): протоколы вставки в корзины, публикации
  чанков, захвата разделов и фаз барьера моделируются тем же Rust-кодом с атомиками под cfg(loom) (loom::sync::atomic вместо std), loom
  перебирает все чередования 2–3 потоков; инварианты — ни одна вставка не теряется, чтение видит только опубликованные чанки, раздел
  захватывается ровно один раз; запуск RUSTFLAGS="--cfg loom" cargo test --release отдельной целью make loom и в списке проверок
  коммитов раздела 5. Спецификации TLA+ для многофазных протоколов (build → барьер → probe, владение разделами spill, раунды
  repartition), где loom не покрывает межпроцессную семантику барьера и файлов: docs/tla/*.tla с моделью TLC на малых параметрах и
  README о запуске; инварианты те же плюс отсутствие взаимоблокировки; спецификация пишется до кода протокола и обновляется вместе с
  ним. Обычные тесты: SQL-регрессии с параллельными воркерами (force_parallel_mode, max_parallel_workers_per_gather), сравнение с
  серийным планом строка в строку, EXPLAIN ANALYZE со счётчиками воркеров.

  8. Проверить контракт на date, timestamp и text: неподдерживаемые единицы времени, collation и строковые представления должны переходить к Datum. Оптимизированные
  ядра для этих типов добавляются только после завершения начального пути int4.

  Новые callback-и источников добавляются в ABI только вместе с первым реальным потребителем.

  ### 7. Два ядра: PostgreSQL и Greengage 7

  Решение 2026-09-22: Tessera проектируется на одно дерево и один набор модулей для PostgreSQL и Greengage 7
  (~/git/greengage, ветка 7x-mac, PostgreSQL 12.22, установка ~/git/greengage/build, демо-кластер: координатор 7000,
  три сегмента 7002–7004). Различия ядер не размазываются по логике, а собираются в узкие швы; Greengage даёт таблицы
  AO/AOCO и сжатие, которых у PostgreSQL нет. Раздел заменяет приложение «Переносимость на Greengage 7» от 2026-09-20.

  Что выяснено (по исходникам форка, 2026-09-22). Наш постраничный итератор по heap работает на форке: heap_getnextslot
  один раз на страницу, затем rs_vistuples/rs_ntuples/rs_cbuf/rs_cblock и перемотка rs_cindex — поля и heapgetpage
  (heapam.h:46-72, :116) те же; видимость решает ядро (HeapTupleSatisfiesVisibility в форке берёт ещё Relation ради
  распределённых снимков, мы её не зовём). Меняются четыре места: описатель атрибутов (в PG 12 нет CompactAttribute,
  есть Form_pg_attribute.attcacheoff), table_beginscan с четырьмя аргументами и без SO_HINT_REL_READ_ONLY, учёт
  статистики (t_counts.t_tuples_returned) и блок параллельного скана. Точечных расхождений API около двадцати:
  foreach_ptr/foreach_int/foreach_delete_current (список PG 12 связный, lnext с одним аргументом), repalloc0_array,
  MarkGUCPrefixReserved → EmitWarningsOnPlaceholders, имена F_SUM_INT4/F_MIN_INT4/F_MAX_INT4/F_COUNT_/F_COUNT_ANY (в
  форке макросов для агрегатов нет; OID устойчивы: 2108, 2132, 2116, 2803, 2147), commands/explain_format.h,
  set_deparse_context_plan + es->rtable_size, custom_restrictinfo, varreturningtype, compute_gather_rows, create_agg_path
  с лишним bool streaming, table_beginscan(_parallel), типизированные колбэки expression_tree_walker/mutator,
  pg_always_inline/pg_assume; только в тестах — InstrAllocNode, PG_FINALLY, TupleDescFinalize. Наш код опирается и на
  поля master, которых нет в PostgreSQL 18: firstNonGuaranteedAttr, tts_first_nonguaranteed, fetch_att_noerr,
  first_null_attr, align_fetch_then_add, ScanRelIsReadOnly.

  Что в форке иначе по существу. (1) ORCA включена по умолчанию и обходит хуки путей целиком (planner.c:380-406):
  нужен optimizer = off. (2) Параллельных запросов PostgreSQL нет (parallelModeOK = false, planner.c:483-503): слой DSM
  собирается, но мёртв. (3) План уезжает на сегменты через outfast/readfast: CustomScan с custom_private
  сериализуется, методы восстанавливаются по имени (readfast.c:1013) — модули предзагружаются в каждом сегментном
  бэкенде через gpconfig -c session_preload_libraries и gpstop -u (SET на сегменты не уезжает). (4) Path несёт locus,
  motionHazard, rescannable: tess_path_create копирует шаблон целиком, пути над SeqScan наследуют распределение.
  (5) Агрегация двухстадийная: первая стадия в UPPERREL_CDB_FIRST_STAGE_GROUP_AGG, затем cdbpath_create_motion_path
  и финальный create_agg_path (cdbgroupingpaths.c:981-1091); хук create_upper_paths_hook для UPPERREL_GROUP_AGG
  вызывается после этого. (6) ExecSquelchNode (execAmi.c:717) не знает T_CustomScanState и падает по умолчанию;
  squelch зовут LIMIT, Motion, соединения, сортировка — без правки форка ничего не запускать. planstate_walk_kids не
  спускается в custom_ps (статистика EXPLAIN с сегментов), plan_tree_mutator не мутирует custom_plans/custom_exprs
  (коррелированные подзапросы). (7) ExplainCustomScan работает только на координаторе: наши счётчики там нули; с
  сегментов текст едет через cdbexplainfun/cdbexplainbuf. (8) Сборка: -Werror в CFLAGS форка, суффикс .so, NO_INSTALL
  не поддержан, PG_MODULE_MAGIC с полем product — модуль обязан собираться против заголовков форка.

  AOCO даёт настоящие колонки. Для типа фиксированной ширины значения блока лежат подряд (datum_beginp, шаг
  typeInfo.datumlen; datumstreamblock.c:747-748), сжатие zlib/zstd снимается целиком до доступа к значениям
  (datumstream.c:1213-1222), блок по умолчанию 32 КБ (≈8000 int4). Плотность ломают NULL (значения ужаты, позиции в
  null_bitmap), compresstype=rle_type (повторы хранятся один раз) и дельта-сжатие — там чтение по одному через inline
  datumstreamread_advance/_get (utils/datumstream.h:195-241). Видимость — запись карты на 32768 строк с обычным
  Bitmapset (appendonly_visimap_entry.h:60): проверяется рядом, не строкой. Заголовки cdb/cdbaocsam.h,
  utils/datumstream*.h, access/appendonly_visimap*.h устанавливаются. Помеха одна: статические функции открытия
  следующего файла сегмента (aocsam.c:422, 479) — затравка через aocs_getnext на границе файла либо экспорт в патче
  форка. AO по строкам: VarBlockReaderGetItemPtr даёт указатели на 64 memtuple, memtuple_getattr с фиксированным
  смещением из MemTupleBinding — аналог heap-курсора, без быстрой колоночной ветки.

  Архитектура: одно дерево, общий код, узкие швы.
  - include/tessera/compat.h — единственный заголовок с проверками PG_VERSION_NUM/GP_VERSION_NUM: макросы-итераторы,
    имена функций агрегатов по OID, tess_table_beginscan(rel, snapshot), tess_deparse_context(es, planstate),

    возможностей: TESS_PARALLEL_QUERY (1 на PostgreSQL ≥ 13 без GP_VERSION_NUM, 0 на Greengage), TESS_COMPACT_ATTRS
    (PostgreSQL ≥ 18), TESS_GUARANTEED_PREFIX (master). Подключается через tessera/abi.h.
  - Метаданные деформации свои: рантайм один раз на описатель строит TessDeformLayout (кэшируемые смещения ведущих
    атрибутов фиксированной длины, первый некэшируемый атрибут, гарантированный префикс из attnotnull, attlen > 0,
    attbyval, !atthasmissing; где доказать нельзя — 0). heap_deform.h и heap_batch.c читают только этот слой и
    публичные макросы tupmacs.h; зависимость от master снимается и для чистого PostgreSQL 18. Быстрая ветка через

  - Параллельный слой под TESS_PARALLEL_QUERY: shared_stats.c, пять DSM-колбэков трёх узлов, parallel_divisor,
    частичные пути в nodes/planner.c и create_partial_paths в nodes/agg.c; в публичном заголовке storage/dsm.h и

  - Источники — отдельные модули, общий вход: узлы nodes/ общие; источники форка — модуль sources/aocs/

  - Шов «сборка частичных результатов» в TessAgg: частичный режим (AGGSPLIT_INITIAL_SERIAL) есть; на PostgreSQL части

  ## Документация и проверки

  Каждый коммит обязан содержать:

  - комментарии ко всем новым открытым типам и функциям;
  - описание владения, времени жизни, ошибок и параллельного доступа;
  - небольшой компилируемый пример использования;
  - функциональные тесты;
  - сравнение результатов нативного и принудительного Datum-пути для каждого нового типа и операции;
  - измерение производительности, если меняется горячий путь.

  Проверки:

  - cargo fmt --check;
  - cargo clippy --all-targets -- -D warnings;
  - Rust-тесты в обычной и release-сборке;
  - cargo test -p tessera-capi --benches: правильность всех случаев бенчмарков без счётчиков и root;
  - полный прогон tessera-bench (около 40 с, под sudo -v) для коммитов, меняющих горячий путь;
  - C-тесты размеров, выравнивания и старых укороченных ABI-структур;
  - SQL regression tests в assert- и release-сборках PostgreSQL;
  - отдельная проверка двух независимо собранных расширений через мост;
  - проверки NULL, пустых выделений, пачек меньше и больше 64 строк, повторного сканирования и ошибок жизненного цикла.

  Для горячих путей выполняются одинаковые сценарии на Tessera и pg_batch. Постоянные бенчи сравнивают счётчики на вызов: инструкции
  решают (предел роста 1%), такты предупреждают (3%) и проваливают только явные замедления длинных операций (минимум по блокам трёх
  процессов, 10% от 500 тактов), промахи ветвлений объясняют разницу в тактах; время не измеряется. Отставание
  от эталона показывается отношением инструкций и не влияет на статус. Постоянный бенч фильтра не требует PostgreSQL или C-компилятора,
  но требует root для счётчиков. При подтверждённом превышении порога перенос останавливается для профилирования и обсуждения;
  несогласованный счёт не считается успешной проверкой.

  Сообщение коммита объясняет мотивацию и изменение; абзац Validation: перечисляет выполненные проверки как команды, без чисел и статусов.
  Строки ограничиваются 72 символами, между предложениями используется один пробел.

  ## Принятые ограничения

  - pg_batch на коммите 0de9c95 используется только как образец; его грязный подмодуль nanoarrow не переносится и не изменяется.
  - Исходная совместимость с PgBatch* не сохраняется.
  - На первом этапе поддерживается PostgreSQL master; с раздела 7 — также Greengage 7 (PostgreSQL 12).
  - Общий IR, JIT, стоимостная модель и проталкивание агрегатов в источник пока не входят в перенос.
  - Начальные выражения, агрегаты и hash join сохраняют проверенное ограничение int4.
  - ABI не связывает один тип PostgreSQL с одним физическим форматом колонки.
  - Счётчики производительности: macOS через kperf (root, приватный API); бэкенд perf_event_open для Linux появляется вместе с CI;
    другие ОС для измерений не поддерживаются.
  - Исправление, требующее нового публичного API, другой модели владения или новой архитектуры, останавливает работу до согласования.
